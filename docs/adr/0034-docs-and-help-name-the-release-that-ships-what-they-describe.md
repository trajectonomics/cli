# Docs and help name the release that ships what they describe

A document or a help page that describes something the latest release does not have names the release that will ship it. The installer-facing README carries that as one visible line, `> **Ships in X.Y.Z.**`, at the top of the `## ` section it covers, and the line ends at the next `## ` heading. Help carries it as an optional note on the command definition, printed under the summary on that page, in the form `ships in X.Y.Z`. Nothing else may promise an unreleased command: a section or page without a marker describes only what the release you are running has.

On 2026-11-15 this repository's README promised `projection run`, `projection compare`, `fi` and `scenario tax` while `npm dist-tags.latest` served `0.1.0`, which has none of them; `traj help baseline` on that release said "Show the Baseline a Projection starts from", so its own help sent a reader to a command the same binary answers with `unknown_command`. A generated listing cannot lie — a release's `traj help` lists only the commands that release has — so only categorical prose needs a marker, and `baseline show` needs one even though it ships in `0.1.0`: the note is about the word the page uses, not about the command being absent.

Two checks keep the markers true. Offline, `bun test` asserts that every command the README names exists in this tree or lies inside a marked section. Online, a workflow job reads the latest release's own `traj schema` output — `npm view @trajectonomics/cli dist-tags.latest`, then `npx @trajectonomics/cli@<version> schema --json`, retrying through the npm-first window ADR-0023 records — and fails a pull request that names a command that release cannot run without a marker. A weekly run adds the freshness rule: no marker or note may name a release that is not newer than the latest, so a marker is removed once it has shipped instead of rotting. The release workflow does not run the check: npm publishes before the binaries exist, so a gate there could not prevent anything, and a published version is spent.

`traj schema` does not carry the note. Usage and `traj schema` are built from one set of definitions so they cannot drift (ADR-0010, ADR-0015), and a release annotation is reader-facing prose rather than part of what a command accepts or returns. Exposing it would commit a public field that only informs a reader who already has the commands, because a release that lacks a command does not list it. This is the one deliberate exception to "usage and schema come from the same definitions", and it is scoped to release annotations; a flag, an input field or a result key is still described in both places or in neither.

## Considered options

Deleting the section until the release that ships it was rejected: it removes the one thing the reader wants, and it does nothing for the install front door or the help page. An HTML comment as the marker was rejected because the reader who needs it cannot see it. A `shipsIn` field printed on the command it appears on was rejected because it would be false on `baseline show`, which ships in `0.1.0`. Matching every summary against a list of unreleased terms was rejected because it misses the pages that do not repeat the term — `fi`'s summary says "financial independence", the `projection` group says "Project the future" — and a list of terms is a second source of truth beside the definitions. Reporting a stale marker as an issue instead of failing a run was rejected as the only mechanism: the weekly run is that report, and the pull request that introduces a marker is where its freshness is cheapest to get right.

## Consequences

A release that ships marked work leaves a stale marker until the next pull request or the weekly run reports it, so `docs/runbooks/releasing.md` tells the release cutter to land the marker-clearing pull request *before* dispatching that release: a marker left in place is wrong for good in that release's help and in the README of its tag. The check needs the network for the released schema, so it is a workflow job and never part of `bun test`; `bun run check` stays offline and deterministic (AGENTS.md rule 4). When the version named by a marker is cut differently than the marker says, the marker stays true — it names a release that has not happened — and the freshness rule reports it only if that release never ships the work.
