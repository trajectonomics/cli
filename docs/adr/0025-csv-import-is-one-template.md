# CSV import is one template, one transaction, keyed by external reference

Bulk `tx import` accepts exactly one CSV template, whose header is `date,from,to,amount,memo,external_ref,project`. One row is one simple two-posting Transaction: `from` is the source Account, `to` the destination, `amount` a positive decimal magnitude in the destination's currency, `memo` free UTF-8, `project` a Project Dimension on both Postings, and `external_ref` required. Opening balances, more than two Postings, corrections, multi-currency and account creation stay on `tx add` or out of scope. A wrong header, a malformed row, an empty file or invalid UTF-8 is invalid input at exit 2; a row-level rejection keeps the class of its own Error code.

The import is all-or-nothing. The command builds every row, writes them in one `IMMEDIATE` transaction, and if any row is rejected it rolls the whole batch back and returns every rejection in the error envelope's `details.rows`. A success reports `added` and `duplicate` rows; a rejection is not a success result. The rejected row with the highest Exit code, ties by earliest line, supplies the envelope's code and class; every row's own code and class stay in the details. This follows ADR-0013 and ADR-0021: a command returns a Result or an AppError, and exit 0 means it wrote or the world already matched. It also follows ADR-0019: `--dry-run` runs the same batch and rolls it back, with every generated id null.

`external_ref` is the only idempotency key. It is unique in the personal entity; replaying it with identical content is a duplicate, with different content a conflict. A row whose Transaction was later voided or amended is still a duplicate and is not re-added, because the reference remains on the original and an amendment's replacement cannot reuse it. No content hash is computed or stored. The issue's "or content hash" alternative was rejected: two genuinely identical Transactions on one day are not the same row imported twice, and the Ledger has no Transaction content index. ADR-0012 already names `external_ref` as the key.

`--template` prints the header and opens no data directory. `-` reads the CSV from stdin; it extends ADR-0020's `-` rule from a document field to a positional. The reader is a small in-repo RFC 4180 parser with strict UTF-8, a stripped BOM, LF/CRLF/CR normalization and quoted-field support; it adds no dependency. A header-only file is a successful no-op.

## Considered options

Partial commits were rejected because the CLI contract has no partial success: a partial import would either exit 0 while rows were rejected, or write rows on an error path. A content hash was rejected for the reason above. A group column that assembles multi-posting Transactions from several CSV rows was rejected because it turns the one template into a second transaction format; `tx add --postings` already serves that case. A second template, or bank-specific CSV, OFX or QIF parsing, was rejected by ADR-0012. Printing a sample row with the template was rejected because a user who saves and imports the template would import fake data.

## Consequences

The header is a wire contract: adding a column is a breaking change to the template that external prompts and scripts target, so it needs a new decision, not a quiet extension. A single bad row blocks the whole file; the error lists every rejection and a dry run previews the outcome, so the user fixes the file and re-runs rather than repairing a half-imported Ledger. The reference must be stable across reads of the same source and unique across the personal entity, so users should prefix it with the source (`kbank:...`). The `line` in a `line.N` path is a physical CSV line, not the avoided synonym for a Posting.
