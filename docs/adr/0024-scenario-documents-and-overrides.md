# Scenario documents are `sim-core`'s, and Overrides use dotted paths with stable ids

`sim-core` owns the Scenario model (AGENTS.md rule 5). A Scenario document is validated by `@trajectonomics/sim`'s `check()`, called with an empty Baseline v1 and no Timeline. The CLI keeps only the problems whose path starts with `scenario.` and drops `MISSING_CARRY_IN`, which depends on the Timeline's start and so belongs to `projection run` (#11). A failure is `invalid_input` at exit 2, at the failing document path, carrying `sim-core`'s code; `details` lists every problem in the core's order, which is why `parseDocument` forwards the code too. The same validator runs in the command's document form, in the Store's canonicaliser and on the final document of `scenario fork --set`, so `traj schema`, an apply, a fork and a restore cannot drift. The pin is exact (`0.1.0`, Scenario version 1), like `@trajectonomics/ledger`'s. The Spec was written against the `0.2.0-alpha.15` alpha (Scenario version 4), but #73's Baseline mapping landed first, so this branch took the pin the Spec's cross-repo rule names: whichever of #73 and #70 lands second moves to the other's pin. The supported `schemaVersion` is never hard-coded in the CLI: `sim-core` answers with `UNSUPPORTED_SCHEMA_VERSION`. The CLI does not grow a second Scenario model: its zod layer accepts any JSON value and defers to `check()`, and `traj schema` prints only that a document is an object with a `schemaVersion`, plus the validator's name and pinned version.

An **Override** is a value that replaces one dotted path of a Scenario document. It is persisted only by `scenario fork --set`; a Projection applies the same Override transiently. The path grammar is shared with #11: object keys separated by dots, and list items addressed by their stable string `id`, never by array index. A literal `.`, `\` or `=` in a key is escaped with `\`; any other escape is invalid. Values are JSON literals, so a number stays a number and a string is quoted.

`--set` only replaces a path that already exists. A new key is indistinguishable from a typo, and the issue requires a typo to fail with a hint. A set may not change a list item's `id`; identity cannot be rewritten through a whole-item replacement. A list without stable ids can only be replaced whole by setting the list's own path. Sets apply in command-line order; an exact duplicate path is refused. An unknown path is `invalid_input` at exit 2 with `details.index`, `details.path`, `details.segment` and `details.suggestion`. The suggestion is the nearest key or id by case-sensitive Levenshtein distance when it is close enough, otherwise the hint lists the known siblings. Lookups use own properties, so prototype names never resolve. A document the overrides leave outside `sim-core`'s schema is reported at the set whose path covers the problem, or at the last set when no set's path does; `details.documentPath` is the path inside the document.

`scenario diff` uses the same path formatter and id-keyed-list rule. It matches list items by `id`; if the common ids appear in a different relative order, the list itself is one atomic `changed` entry and its descendants are suppressed. `identical` is true only when the change list is empty, which is deep equality under those rules.

A live Scenario name is a conflict at exit 5, with the new `scenario_name_taken` code carrying `details.scenarioId`, mirroring `account_name_taken`. `scenario rm` tombstones rather than deletes and frees the name for reuse. Because a tombstone never resolves and a freed name may already belong to a new Scenario, a retry of `rm` is `not_found` at exit 4 rather than an idempotent success; this is the deliberate exception to ADR-0021's retry rule.

## Considered options

Blocking Scenario commands on `sim-core` was rejected: the Store already accepts Scenario documents, the command surface is useful before projections exist, and ADR-0017 records how the Store writes and restores the document's canonical bytes. Inventing a Scenario schema in the CLI was rejected as a competing model; `sim-core`'s `check()` is the schema instead, and the document form only prints the envelope-level shape it needs for discovery.

RFC 6902 JSON Patch was rejected for `diff`: it uses JSON Pointer and array indexes, so a user would translate between `/flows/0/amount` for a diff and `flows.salary.amount` for an Override. Positional paths also break when a list is reordered. Treating a bare non-JSON `--set` value as a string was rejected because it silently turns `50000` into a number but `001` into text.

Allowing `--set` to add a key was rejected because a typo would silently create an assumption instead of failing with the required hint. Allowing an item's `id` to change was rejected because every later path and diff would then address a different item, and duplicate ids would make resolution ambiguous.

Returning `already_deleted` at exit 0 for a retried `scenario rm` was rejected: a name-based retry may remove a new Scenario that reused the name, and an id-only exception would give the command two contracts.

## Consequences

The dotted-path grammar and JSON-literal values are a wire contract shared with #11's projection `--set`; both use one pure `applyOverrides` function and echo the applied `{ path, value }` list. `sim-core`'s `check()` is the schema and the path grammar did not change with it. A `--set` that would add a key needs a whole-list replacement or a fresh `scenario apply`.

List order is visible: a reorder is a diff entry, because order may be semantic to `sim-core` and two different canonical hashes must not report `identical`. `scenario rm` is the one mutating retry that reports `not_found` after the end state, and ADR-0021 records that exception.

A restore refuses a Scenario document the pinned `sim-core` rejects, at that interchange row's document path, with the core's code in `details`. A backup written under an older pin may therefore need its Scenario edited before it restores. Bumping the pin to a Scenario version with a different meaning needs its own ticket about stored rows, because a stored row is never re-validated until it is written again; the canonical bytes and `jcs1:sha256:` hash are unaffected by the validation itself. Scenario version 1 has no Levy, so the `MISSING_CARRY_IN` exclusion is a forward guard that no current fixture exercises; a bump to a version with Levies adds the fixture proving a Carry-in problem is the only Timeline-dependent Scenario problem.
