# Tax is the Scenario's Levy, and its Carry-in is the projection's

Tax enters a Projection as one `Levy` from `@trajectonomics/tax`, written into the stored Scenario by `traj scenario tax`, and the CLI holds no tax rule of its own: it turns `--tax th-2026`, `--filing-status`, `--children` and `--children-at-higher-rate` into the profile the core emits that Levy from, and refuses a Flow whose label the core would tally as nothing. A result reports `tax: applied` exactly when its Scenario holds one or more Levies — whichever emitter wrote them, never only the `th-2026-pit` this build writes — `not_applied` when it holds none, and `mixed` for a `compare` whose two sides disagree. The notes name every Levy by its `id`, and only `th-2026-pit` gets the sentence naming Thailand; a Levy the caller wrote is the Scenario's own, so the CLI claims no jurisdiction it cannot see.

The Scenario is the only place both halves can live. `sim-core` refuses a Flow that carries a Tally label with no Levy reading it (`LEVY_REQUIRED`), so a document labelled for tax cannot be stored without the Levy; and the CLI will not store a document it knows the engine rejects. The labels therefore arrive with the Levy, through `--label <flow>=<label>` on the same command, and are removed with it by `--none`.

The Carry-in goes the other way, because it depends on the As-of rather than the plan: it says what a Levy's period had already tallied and prepaid before the Projection starts, so the same stored Scenario projected from two dates needs two answers. The caller states it with `--carry-in` on `projection run`, `projection compare` and `fi`: one JSON document (or `-` for stdin), a flat list of records, each naming its Scenario by name or id, its Levy by id and its period start. The CLI derives nothing.

The periods it needs mirror the engine's own rule: the period containing the As-of when the As-of is not its first day, plus the period before it when that period's Settlement is on or after the As-of; `--horizon` does not move it. The classes a record must name are the `(label, basis)` pairs the Levy's own `tally` measures read — 29 for the Thai Levy — not the plan's labels, because the Carry-in is what the period tallied before the As-of and a salary-only plan can still have had interest or an RMF contribution in the months outside the Projection. `"rest": "0.00"` states the remainder in one line and is echoed expanded. A class nobody stated is an error rather than a silent zero, a class the Levy does not read is refused, and repeating a class or a period is refused.

A period that ended before the As-of is not recomputed. The caller's record is used when it is stated; otherwise the CLI writes the scope record — empty tallies, zero prepaid — only for `th-2026-pit`, whose `due` graph is tally-only (measured: from 2026-01-01 that record closes at exactly the untaxed figure). Any other Levy's required periods are the caller's, because the CLI does not know what a Levy it did not write settles. The echo marks each placed record `flag`, `document` or `scope`, so a reader can tell the caller's figures from the CLI's own assumption, and a stored `levy.carryIn` stays valid under the same class rule as the flag's.

One limit is the engine's and stays there: sim-core shifts a Settlement through the Scenario's resolved `calendar`, and the CLI does not reimplement that. A document that declares a `calendar` therefore gets no derived period and no scope record; the caller's records are placed as given and the engine refuses precisely.

## Considered options

Injecting the Levy at projection time was rejected by the engine, not by taste: the store validates a submitted document with `sim-core`'s `check()`, which refuses a labelled Flow with no Levy, so a caller could never store the labelled Scenario the projection would need. Requiring the user to hand-write the emitted Levy was rejected because the emitter is the core's, and a hand-copied measure graph is a second implementation. Echoing the taxpayer profile from each result was rejected because `sim-core`'s Scenario is strict and cannot hold it outside the measure graph; the stored document is the record, and its hash covers it.

## Consequences

A Projection that starts inside a tax period now needs `--carry-in`: a case that used to reach the engine as `MISSING_CARRY_IN` at exit 3 is refused at exit 2 with the flag named, which is a deliberate contract change. The mid-period note says the year is charged on the Flows from the As-of plus the stated Carry-in, and the sentence that no tax before the As-of is recomputed appears only when the CLI wrote the scope record.

The first version of this ADR was narrower, and the owner overruled it. It said the CLI adds the Carry-in to *this build's* Levy only, leaves a Levy it did not emit untouched, and reported `tax: not_applied` for it; `src/projection-levies.test.ts` pinned that reading. The owner's 2026-11-15 answer on #114 says the opposite — a Scenario the engine charges must never be told its figures are pre-tax — so the Tax status, the note and the Carry-in all follow the Scenario's Levies rather than the emitter's id. The projection no longer injects a Carry-in at all: it takes the caller's, and refuses when one is missing (its own Ticket, #140).

`traj scenario apply` replaces the whole document, so re-applying a Scenario drops its Levy and labels: the caller runs `scenario tax` again. The CLI pins `@trajectonomics/tax` at an exact prerelease, because `emitThLevy` exists only in the `0.2.0-alpha.*` line while `0.1.0` stops at `calculateThTax`; the pin moves only on purpose and re-baselines the taxed projection test (ADR-0031 sets the precedent). A projection that starts mid-year is charged on the Flows inside it and says so, and any tax still owed from before the As-of belongs in the Ledger as a liability rather than in the projection.
