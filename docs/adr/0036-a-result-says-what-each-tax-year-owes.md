# A result says what each tax year owes, and the tax write names what it left out

`projection run`, `projection compare` and `fi` carry `taxYears`: one row per Levy settlement period, from the engine's own `LevyReport` ([ADR-0032](./0032-tax-is-the-scenarios-levy.md)). A row states the Levy's id, the period's `from` and `to`, its `settlementDate`, the `due` before Prepayment, the `prepaid` amount, and `owed` — the engine's own `settlement` field, which is `due - prepaid` and is negative for a refund. `settled` says whether the settlement date falls inside the Projection, and `partial` whether the Projection ended before the period did, so the figure the engine charges and the figure still ahead are both readable and neither is guessed. `taxYears` is `[]` for a Scenario with no Levy, and `projection compare` reports it per side, beside each side's hashes, because one root list would have to mean one of two. The CLI subtracts nothing and holds no rate: the figures are the engine's, in the currency's own money format.

The human format prints the same rows as a `taxYears` table after the annual one (`RenderHint.extra`), so a person reads the March figure the way they read net worth. The assumptions a reader needs are the echo's `tax` status, its `carryIn` records and its `notes`; a row adds the settlement facts. `fi` runs one Projection over the inputs the survival scan already used, because the FI answer does not carry a Projection.

The allowances a Thai employee actually has are flags on `scenario tax`: `--parents`, `--disabled-care`, `--social-security`, `--life-insurance`, `--health-insurance`, `--parent-health-insurance`, `--spouse-life-insurance`, `--mortgage-interest`, `--donation2x` and `--donation1x`, each in THB except the counts. The CLI turns them into `@trajectonomics/tax`'s `ThLevyProfile` and `emitThLevy` applies every statutory ceiling, so no amount is restated here. `--none` also removes the Prepayments that named the removed Levy: a Prepayment is only legal beside its Levy, and leaving it behind made the next read fail with `LEVY_REQUIRED` (cli#150).

The write reports `allowances.stated` and `allowances.notStated`: the deduction classes the flags named and the ones this build supports but the write left out. It is deliberately not "modelled", because that would claim the Levy applies the class, and the CLI would have to reimplement `@trajectonomics/tax`'s eligibility and ceilings to know: a spouse life insurance premium stated by a single filer is read and clamped to zero, and a donation is capped against net income. So the fields report what the write was told and never what the engine applied; the ADR and the field descriptions say so. The class list holds only classes a caller can leave out: `personal` follows the statute and the spouse allowance follows the filing status, so neither is a flag. A contribution class is stated when the emitted Levy has a funded tally measure for its label and a contribution Flow carries that label, read from the Levy's own graph rather than a list in this repository. This is the write's answer because only the write knows the flags: the emitted Levy freezes every fixed allowance into one `allowances.fixed` const whose measure ids are the emitter's `auto.N`, so a Projection cannot recover which deduction classes were stated. A projection row therefore states what the engine applied, and the write states what it was told.

A Projection whose Contributions the engine could not fund adds one note naming the amount, and a compare names the side, because a Contribution larger than the cash available is not made and an RMF what-if against a month with no income otherwise looks identical to its base. The `--carry-in` flag's description now carries the record shape it reads, so `traj schema projection run` describes the document the README was previously the only place to find.

A date's year must be Gregorian and inside 1900–2100. Every date flag takes that check: `--as-of` (projection, baseline, balance and report), `--since`/`--until`, `--date` on `tx add`/`amend`/`void`, `--void-date`, and the `periodStart` of a `--carry-in` record; the check sits in `preparedTransfer` for a built transfer, so a CSV row of `tx import` gets it too, and in the store's correction path for a reversal date, after a standing correction is reported, so a repeated `tx void` or `tx amend` still reports the existing correction before a bad retry date. Each refuses as `INVALID_DATE` at exit 3 with a sentence naming the range and the Buddhist-year trap, except `--horizon`, which is `invalid_input` at its flag because the Horizon is the engine's Timeline ([ADR-0030](./0030-projection-inputs-and-echo.md)). A date typed in the Buddhist calendar reads 543 years later, and `2569-03-01` used to be stored or projected as the year 2569 without a word. Two dates keep the Ledger's own range because the CLI does not narrow them: a birth date, which is historical by nature ([`src/projection-compare.test.ts`](../src/projection-compare.test.ts) pins one before 0100), and a date inside a submitted transaction document, which the core validates. A value off a closed list now names the list in its sentence (`The value is not one of the allowed choices: single, married_joint.`), so a bad `--filing-status` or `--tax` can be fixed from the error rather than from the help page.

## Considered options

Computing `owed` from `due - prepaid` in the CLI was rejected: the engine already states it as `settlement`, and a second subtraction is a second place for the same fact to drift. Deriving `notStated` at projection time was rejected because the emitted graph fuses the fixed allowances into one const measure, so the classes are not recoverable without a second profile store. Writing one Measure per allowance into the Levy was rejected because it would put a tax rule's decomposition in this repository. Storing the profile outside the Scenario was rejected because the store is the CLI's only durable state and a profile column is a hard-to-undo shape for a figure that already has a home in the Levy. Filtering a zero tax year (the prior period a scope record closes) was rejected: zero is a figure a reader may need to see, and the `settled` flag already tells them the charge falls inside the Projection. Restricting the birth date to 1900–2100 too was rejected because its range is the Ledger's and the CLI already pins that a birth date before 0100 is accepted; the other date flags have no such history and a future typo is the harm the range prevents.

## Consequences

Three result schemas grow a `taxYears` array and `scenario tax` grows eleven flags and an optional `allowances` block; the committed projection goldens are re-baselined. A deduction the caller does not state is now reported as not stated rather than silently read as zero, and the tax a year owes is printable from any result instead of being inferred by differencing two Projections. `scenario tax --none` on a Scenario that prepaid tax now writes a document the engine accepts, a Projection says which Contributions it could not fund, and the Carry-in's shape is in `traj schema`. A Projection over a Buddhist year is refused instead of returning a plausible-looking 543-year plan.
